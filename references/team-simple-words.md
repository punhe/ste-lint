# Team simple words

Use this list when you write for a teammate. The reader may not speak English as a first language. Prefer a short word. Prefer a picture. Prefer less text.

Load this file with `ste-writing` for:

- Canonical SOPs and checklists
- Notion process pages
- Linear issues, comments, and Linear documents for the team
- Development wiki notes that humans will read
- Other shared guides (process pages, review pages)

Do not use this list to rewrite owner-only notes, client marketing, or legal boilerplate.

Do not bulk-rewrite old pages. Apply the list when you create or edit a page.

## How to write

1. Use one name for one thing on the whole page.
2. Put a **Words on this page** box near the top when the page uses more than two terms from the table. Explain each term like you would to a child.
3. In the box, you may show the old name once in italics so people still recognize it in Linear.
4. After the box, use only the simple name.
5. Keep product names: Linear, Linear issue, Linear comment, Notion.
6. Prefer a picture, a two-column example, or a three-step diagram over a long paragraph.
7. Cut each idea to one short sentence plus one "Do this" line when you can.

## Preferred names

| Use this | Do not use on the page | Child meaning |
|---|---|---|
| Project summary | brief (except as an old name in the word box) | The one short document that says who the site is for, what we will make, and what is decided. |
| Pass the work | handoff | You finish your part and write what the next person needs. |
| Big problem | material finding | A problem that would confuse a visitor or hide the next button. Fix it before you pass the work. |
| Design option | concept | One full look for the site, shown on a computer and a phone. |
| Built site | implementation (in process docs) | The real website you can click. Not only a picture. |
| Reviewer | specialist | The person or helper who checks one kind of work. |
| Who it is for | audience | The people we want to visit and take action. |
| A guess | assumption | Something we think is true. We do not have proof yet. |
| The next step | conversion (in process docs) | The action we want: book, buy, or ask. |
| What to keep from examples | reference traits | The look or feeling we copy from sites we like. |
| The cost of the choice | tradeoff | If we pick A, what we lose from B. |
| Match / stay with | aligned | The work still follows the client goal. |
| Looked at / problems found | inspected / findings | Someone opened the real page and wrote what is wrong. |
| Not decided yet | unresolved | An open point. Name the owner. |
| Two answers | conflict | Two people want different things. Write both. Pick an owner. |
| Later checks | gates / coverage | Reviews we want later. Not the job list today. |
| What people type and want | search intent | Why someone searched. The page should answer that. |
| Limits | constraints | What we cannot change: time, money, brand, tools. |
| Start here | the spine | The first questions or steps. Read these first. |

## Keep these names

Linear. Linear issue. Linear comment. Review page. Desktop. Phone. Client. Launch. Staging. Notion.

## Analytics and code

On a GA4, GTM, or Ads page you may keep the word **conversion** when it is the product label. Define it in the word box.

On a developer SOP you may keep **implementation** when it means code or a deploy step. Define it in the word box if the Project Manager section uses **built site**.
